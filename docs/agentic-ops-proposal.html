IRIS-HEP · Design proposal

EWKit Agentic Ops

A web app that runs EWKit n-tuple productions for the analyses already in the EWKit repository on the UChicago Analysis Facility's HTCondor pool, watches the jobs with a LangGraph agent, and proposes fixes that a person approves before anything changes.

Summary

EWKit is the EW SUSY group's package for producing analysis n-tuples with the ATLAS CP algorithms. Every analysis already lives in the repository as a folder under data/, holding a YAML config and lists of DAOD datasets. Today those productions go to the grid through EWGridRun.py, and the analyser monitors and retries PanDA tasks by hand.

This proposal adds a supervised way to run the same analyses on the UChicago Analysis Facility. The app connects to the EWKit repository, offers a run for any analysis folder at any branch or tag, checks the inputs, runs a test job, submits to HTCondor, and then monitors the production. Before submission, a builder agent drafts the run's options from a plain-language request and a reviewer agent explains what the input checks found. When something goes wrong during the run, the monitoring agent explains the problem and proposes a fix, which a person approves before it is applied.

It combines five pieces:

  • EWKit on gitlab.cern.ch: the analysis configs, the DAOD lists, the run script EWRun.py, and the container image its CI already builds.
  • The UChicago AF MCP Platform (atlas-af at mcp.af.uchicago.edu), a credential-brokered gateway to Rucio, AMI, HTCondor and the AF filesystem. It resolves datasets and runs and inspects the jobs.
  • LangGraph for durable, checkpointed graphs: one that checks and submits a run, one that monitors it for hours or days.
  • A FastAPI service that hosts those graphs and holds the GitLab credentials needed to read EWKit.
  • CopilotKit for the web app, which shows live production state and renders proposed interventions as approval cards.

The governing rule is unchanged: the model proposes, deterministic code executes, and a person approves anything that spends compute or writes data. In this revision the app never writes to the EWKit repository, and no model writes or edits configs. The run setup agents only draft and critique a run specification, the options passed to EWRun.py; deterministic code decides whether it is valid, and the person accepts every change.

Goals and scope

Goals

  • Any runnable analysis folder in EWKit can be produced on the UChicago AF from a few choices in the web app, with no local setup.
  • No production starts without passing input checks, a passing test job and an approved cost estimate.
  • Problems in a running production are noticed within minutes, explained in plain language with evidence, and paired with a concrete fix.
  • Outputs carry the same names EWKit's grid productions use, so downstream tooling keeps working.
  • Every run is reproducible from its EWKit commit, image digest and run options.

Out of scope for now

  • Creating new analyses, or editing configs and sample lists. Changes go through EWKit merge requests as they do today.
  • Agent-written configs and agent sample discovery, including the TopCPToolkit skill used in earlier drafts.
  • Grid submission through PanDA (EWGridRun.py). See D10.
  • Writing anything back to the EWKit repository. See D7.
  • Fully autonomous remediation with no human in the loop.

EWKit at a glance

EWKit builds on AnalysisBase 25.2.108 and the central CP algorithms, with a few EW SUSY specific algorithms of its own. It is independent of TopCPToolkit, although its configs use the same CP algorithm YAML blocks. The facts below come from the repository at 17c998c and shape most of this design.

How a job runs

  • EWRun.py --analysis <Folder> picks up data/<Folder>/config.yaml; --configName selects another file such as config_sys.yaml
  • A config may start with Extend: '../Other/config.yaml' and override only some blocks
  • Run options: --doSys, --noSys, --noFilter, --noThinning, -e for an event limit, and -PS to print the algorithm sequence and branches without processing events. -PS still needs an input file: the run script reads the file's metadata (data or MC, Run 2 or 3, generator) while building the sequence
  • EWRunScript.py also changes settings per analysis and per Run 2 or Run 3 at run time, so the YAML alone does not fully describe a job. Jobs must therefore name the folder with --analysis
  • An Extend: config is merged into a config_extended.yaml written next to it in the installed data/ folder, which may fail when the image is mounted read-only
  • Some configs turn systematics on by default (runSystematics: True in CompressedSleptons, DisplacedTrack, SUSYEWK1L2L), with no _SYS in the output name unless --doSys is given

What already exists

  • CI builds an RPM and pushes a container image to the project registry, tagged with the ref slug. Its workflow: rules only admit merge request and branch pipelines, so tag pushes appear to get no image; to be confirmed with the maintainers. The image records CI_COMMIT_SHA in its environment, so an image can be matched to a commit
  • CI runs four folders (common, CompressedSleptons, RadiativeDecays, DisplacedTrack) on example DAOD_PHYS ttbar and data files. The other folders are not exercised in CI
  • EWGridRun.py submits one PanDA task per dataset and names outputs user.<user>.<analysis>.<DSID>.<sample>.<campaign>.<tag>
  • Full productions must come from a clean, pushed tag. vX.Y tags are protected and created by the maintainers, but most recent tags are per analysis, such as EFP_v6.6, EWK1L2L_v6.4 and SlepWjetFF_v6.0
  • get_ntuples.py --checkStatus --retry is today's manual monitoring and retry tool, for PanDA
  • CODEOWNERS names the owners of each data/<Folder>/

Run lifecycle

A run goes through eight stages. Two are approval gates where the workflow stops until someone signs off. Interventions during the run add further gates, one per proposed fix.

1

Choose analysis

Pick a folder under data/ and a tag, branch or commit of EWKit. The ref is resolved to a commit SHA immediately.

2

Set up the run

Config file, Run 2 and/or Run 3, sample lists (bkg, data, signal…), --doSys and other flags, optional include/skip patterns. Filled in by hand or drafted by the builder agent from a request.

3

Check inputs

Config and Extend chain, sample lists, Rucio resolution, campaign recognition, image availability. The reviewer agent explains the findings and suggests fixes the person can accept.

Gate 1

Approve plan

Manifest, job split, core-hours and output size against the /data quota.

5

Test job

A short-queue job per Run and sample type with -e 1000, then automatic output checks.

Gate 2

Approve launch

Test results, branch list and timing extrapolation. Go or revise.

7

Run and monitor

Full production on HTCondor. The monitor agent proposes fixes, each approved separately.

8

Validate and deliver

Check trees, CutBookkeepers and event counts, then hand over output paths and a provenance record.

Human approval requiredAutomatic

Architecture

Four runtime pieces: a React web app with CopilotKit, a CopilotKit runtime that speaks the AG-UI protocol, a FastAPI agent service running the LangGraph graphs, and the existing UChicago MCP gateway. Postgres holds LangGraph checkpoints, application records and the audit log. The agent service reads EWKit through the GitLab API with a read-only token, and HTCondor workers pull the EWKit image built by EWKit's own CI.

Components

EWKit repository connector

stage 1

Part of the agent service. It reads EWKit through the GitLab REST API at a specific commit and never clones or executes repository code in the service itself. Everything it reads is cached by commit SHA, since a commit's contents never change.

What it reads

  • Branches and tags, so users can pick a ref; each choice is resolved to a SHA
  • The folder list under data/, excluding common
  • Per folder: config*.yaml, every DAODs/Run*_*.txt, any README, and the folder's CODEOWNERS entry
  • The target of each Extend: line, following the chain inside the repository
  • Whether CI has published an image for the ref

How it parses

  • Sample files by pattern, so Run2_sig.txt and Run3_bkg_syst.txt are offered as found
  • # lines become group headings in the UI (e.g. "Vjets: Z+jets")
  • Each dataset name is split into DSID, short name, r-tag, campaign and p-tag
  • The r-tag to campaign map matches the one in EWGridRun.py; unknown r-tags are flagged before submission instead of failing mid-run (D27)

Run setup and input checks

stages 2–3 · Gate 1

The run options mirror EWGridRun.py so they are familiar: analysis, --configName, --runs, --samples, --doSys/--noSys, --noFilter, --noThinning, and include/skip patterns. These options are held as a typed RunSpec. Every check is deterministic code. The run setup agents draft the RunSpec and explain what the checks found, but no model decides whether a check passes.

Input checks

  • The folder is runnable (D9) and the chosen config exists, including its Extend target
  • The config parses and builds: EWRun.py -PS in the EWKit image prints the algorithm sequence and output branches without processing events. It needs one real input file for each Run, data or MC, and DAOD format in the run, taken from a small catalogue of test files reachable through XCache
  • Each dataset resolves in Rucio (read-only) and has replicas reachable from MWT2 or XCache
  • Each dataset's r-tag maps to a known campaign
  • An image exists that was built from the resolved commit (its CI_COMMIT_SHA matches) and can be pulled (D3)
  • Selected sample lists are not empty, and the ref is allowed for the run size (D4)

Plan estimate shown at Gate 1

  • Datasets, files, events and input size per Run and sample list
  • Core-hours, from the test job's events/second, or a calibrated default before the test runs
  • Expected output size against the 5 TB /data quota
  • Queue choice: short (4 h limit) or long (72 h limit), and whether to allow MWT2 overflow
  • Datasets with missing or incomplete replicas, listed

Test, submit and name outputs

stages 5–7 · Gate 2

Jobs run EWRun.py inside the image EWKit's CI built for the chosen ref, pinned by digest so a later push to the same branch cannot change a running production. One HTCondor cluster per dataset, matching one PanDA task per dataset in EWGridRun.py.

Test job checks

  • Exit code zero; the output tree named in the config's Output block exists
  • CutBookkeepers present when the config saves them (config_sys.yaml turns them off); branch list matches what -PS printed
  • One test per Run and sample type, since EWRunScript.py changes settings for Run 3 and for data
  • Events/second and peak memory, used to size the full run

Output naming

  • Same pattern as EWGridRun.py: user.<user>.<analysis>.<DSID>.<sample>.<campaign>.<tag>, with __NOFILTER, __SYS or __NOFILTER_SYS appended when --noFilter or --doSys is used. EWGridRun.py drops the suffix when --submissionTag is set; whether to copy that is part of D4
  • The tag is the EWKit git tag, or a test suffix for untagged refs (D4)
  • Idempotency key per cluster, so a retried submit cannot double-submit

EWKit's share/submit_condor.py is earlier prior art for HTCondor submission. It is tied to one user's paths and Run 2 campaigns, so the app replaces it rather than calling it.

Run setup agents

Run setup is the first place models are used. It is a good place to start: everything the agents need is read-only data the repository connector already serves, nothing they do spends compute, and what they produce is a RunSpec that still has to pass the input checks and Gate 1.

Two agents work around the deterministic validator. The builder turns a request such as "Run 3 background and data for RadiativeDecays at EFP_v6.6, with systematics" into a RunSpec. The reviewer reads the validator's findings and presents the problems as cards with evidence and suggested fixes. Neither agent edits EWKit configs or sample lists, and neither decides whether a check passes. A fix is a change to the RunSpec, which the person accepts, edits or dismisses, after which the validator runs again.

Builder agent

  • Returns a RunSpec, a one-line reason for each field it set, a list of assumptions, and questions where the request is ambiguous
  • Asks instead of guessing. For example: "with systematics" when the config already turns them on, or "signal" for a folder whose lists are named sig
  • Leaves the ref as typed; code resolves it to a commit and records both

Reviewer agent

  • Returns issue cards: severity, title, explanation, evidence and an optional RunSpec patch
  • Groups and ranks the validator's findings and explains them in plain language
  • Adds judgement the validator cannot make: the spec does not match the request, a very large signal list when a subset was probably meant, or a folder never run in CI, which makes the test job matter more
  • When the fix is a change to EWKit, it says so, links the file at the commit, and names the folder's code owners, as the monitor does

Rules enforced in code

  • Every card must cite a validator finding, or a file and line at the commit. Cards without evidence are dropped
  • Every patch must validate against the schema, and the validator runs again before the person sees the result
  • Both agents read at the resolved commit, never at a moving ref
  • Repository text reaches them only inside delimited evidence blocks
  • The builder and reviewer run as separate graph nodes with separate prompts and no shared conversation
  • The model IDs, prompt versions and accepted patches are recorded with the run

Build order. The RunSpec schema and the validator come first, because the reviewer is only as good as the findings it is given; without them it would make up problems or miss real ones. The builder comes next, then the reviewer. The validator and Run setup form are useful on their own if either agent turns out not to be.

Handling rules

  • Stored as Kubernetes secrets and mounted only into the agent containers; the web container never sees them
  • Never sent to the browser or to the model, and never written to logs or the audit trail
  • The service talks to GitLab only through a small client that allows read endpoints, so a bug cannot turn into a write
  • An expiry warning in the operator view 30 days before any token lapses

Why not the alternatives

  • Deploy tokens allow git clone and registry pulls but not the REST API the connector uses
  • A personal access token ties the service to one person's account and permissions
  • Per-user OAuth would let the app see exactly what each user can see, but adds a GitLab login on top of SSO. Worth it only if per-user visibility matters, which it does not while every user reads the same repository

Monitoring agent

The monitor is a LangGraph graph with one thread per production, checkpointed in Postgres so it survives restarts. Each check is a short run triggered on a schedule, which keeps load on the schedd predictable and lets a production be paused by not scheduling the next check.

Detection is rule-based and cheap: state counts, hold reasons, exit codes, time spent idle, throughput against the plan. The model is called only when a rule fires, to read the evidence, diagnose the cause and draft an intervention from a fixed catalogue. It plays the role get_ntuples.py --checkStatus --retry plays for PanDA today, with explanations and approvals added.

What it watches

  • Job state counts per cluster: idle, running, held, completed, removed
  • Hold reasons, e.g. memory over request, proxy expired, file transfer failure
  • Idle time beyond the norm, with the equivalent of condor_q -analyze
  • Failed exits, with the tail of stderr matched against known CP-algorithm, EWKit and XRootD error signatures
  • Throughput against the Gate 1 estimate
  • Output files arriving in /data, opened with uproot for a quick check

Completion criteria

  • Every input file was processed exactly once, or an explicit, approved exclusion list exists
  • The sum of CutBookkeeper initial events matches the dataset's event count from Rucio or AMI metadata
  • No output file is empty or missing the output tree
  • A provenance record is written next to the outputs

When to stop retrying and accept a partial production is D23.

Deployment

The system ships as two container images, a web image and an agent image, plus Postgres. Both sit behind one hostname, so the browser sees a single origin. The EWKit image is not ours to build: EWKit's CI already produces it.

The agent image runs as two processes that share Postgres:

  • agent-api serves the AG-UI endpoint, the REST API for analyses, runs and the audit log, and the optional GitLab webhook. It holds no state of its own, so it can scale to several replicas.
  • agent-worker runs scheduled monitor checks, repository polling and submission steps. One replica at first, which avoids leader election.

A third process runs from a different image:

  • ops-executor holds the grid credential and the grid clients. It runs a closed catalogue of typed operations, such as rucio_list_replicas, condor_submit and condor_rm, for the execution node only. It has its own ServiceAccount, accepts traffic only from the agent pods, and its egress is limited to grid endpoints. See Grid credentials for procedural ops.

Web app: one Node container

CopilotKit's React SDK talks to the CopilotKit Runtime, a small Node service that relays to the agent service over AG-UI using LangGraphHttpAgent. With Next.js, the runtime lives in the same container as the pages at /api/copilotkit. A Vite build would need a separate small Node container for the runtime. GitLab Pages is not recommended, because the API would sit on another domain.

Topology

Environments

  • Local: Docker Compose with Postgres, the agent image and the web app. A stub MCP server replays recorded job histories, and a local checkout of EWKit stands in for the GitLab API.
  • Staging: its own namespace, the real MCP gateway with a test account, reading EWKit read-only like production.
  • Production: its own namespace, with Postgres backed up and the audit log retained per D22.

Build and release

  • GitLab CI in our own repository builds the web and agent images and pushes them to its registry
  • Tagged releases deploy to production; the default branch deploys to staging
  • Deployment tooling (Helm, Kustomize or Argo CD) is D26

Data model

Application records live in Postgres next to the LangGraph checkpoints. The checkpoint is the agent's working memory; these tables are the system of record that the UI and audit log read. Configs and sample lists are not copied as editable records: a run refers to them by commit SHA and path.

Safety and trust

Guardrails

  • Typed intervention catalogue; no free-form shell or condor_* commands from the model
  • Run setup agents have only read-only repository tools. Their output is a RunSpec or a patch to one, validated by code; they never decide that a check passed
  • Per-run caps on jobs, core-hours and output size, enforced in code
  • A kill switch per run and a global one for operators
  • Write tools available only to the execution node, never to the diagnosis node
  • Approvals expire if the underlying state has changed since the card was created
  • Read-only access to EWKit, enforced by both the token's scope and the client code

Untrusted input

  • Job stdout and stderr, dataset metadata, and repository content (YAML comments, READMEs, commit messages) are data, not instructions. They reach the model only inside clearly delimited evidence blocks.
  • Nothing read from a log or the repository can widen the agent's permissions or skip an approval, because policy checks run in code after the model responds.
  • Repository code runs only inside the EWKit image on HTCondor workers, never in the agent service.

Accountability

  • Every MCP call runs as the requesting user through the broker, so facility logs show who acted
  • The audit log records which model produced each proposal
  • Provenance next to the outputs: EWKit commit and tag, image digest, analysis, config file, run options, dataset list, approvals

Evaluation

Run setup agents

  • Builder: a set of requests with the RunSpec each should produce, including ambiguous ones where the right answer is a question
  • Reviewer: specs with known problems, many taken from master as it is: r17610 in DiTauStudies, its empty Run 3 signal list, the blocked SUSYEWK1L2L, an untagged ref for a full production, an Extend folder, a request that does not match its spec
  • Metrics: problems caught, false alarms, cards without usable evidence, and how often people accept the suggested patch
  • Rerun at each EWKit tag and each prompt change

Monitoring

  • Recorded job histories replayed through the graph: held for memory, proxy expiry, bad replica, slow site, a corrupt input file
  • Metrics: time to detection, correct diagnosis rate, false alarm rate, approval acceptance rate
  • Shadow mode in production first: the agent proposes, nobody acts, and operators compare its proposals with what they did

Runs and outputs

  • For each runnable folder, a small AF run compared against the same datasets' grid n-tuples from data/<Folder>/ntuples/, where those lists exist: same branches, same event counts
  • Input checks run against every folder at each new EWKit tag, to catch unknown r-tags and missing replicas early

Delivery plan

M0 · Spike

Confirm the platform

Read EWKit's data/ tree with a project access token. Run the EWKit image on one AF worker against one DAOD file. List the actual HTCondor tools on atlas-af, submit one job through MCP and read its log back. Test credential delegation for a long-running agent.

Exit: D1, D2, D3, D5 and D13 decided.

M1 · Analyses and runs

Choose, check, test, launch

Repository connector (done: the campaign browser), Analyses and Run setup screens, the RunSpec schema and validator, then the builder and reviewer agents, Gate 1 with cost estimate, test jobs, Gate 2, full submission with EWGridRun-compatible output names. A minimal dashboard shows job states; monitoring is still manual.

Exit: one real production of one folder delivered, with outputs matching the grid n-tuples for the same datasets. The reviewer catches the known problems on master in its evaluation set.

M2 · Read-only monitor

Detect and explain

Monitor graph in shadow mode: detection rules, model diagnosis and proposed approval cards, with no execution.

Exit: false alarm rate and diagnosis accuracy acceptable on replays and live runs.

M3 · Approved actions

Turn on interventions

Execution node, approval cards that resume the graph, verification, notifications. Low-risk catalogue entries first.

Exit: interventions executed safely on real productions.

M4 · Pilot

EWKit analysis teams

Two or three analysis teams run real productions. Add the operator view, kill switch, token-expiry warnings and user documentation.

Exit: go or no-go for all EWKit analyses.

Later, not scheduled

  • A PanDA backend that runs EWGridRun.py, so the same monitor and approvals cover grid productions (D10)
  • Proposing merge requests that update ntuples/*.txt after a production, as get_ntuples.py does for grid outputs (D7)
  • Agent help with sample list upkeep, such as p-tag updates in the style of update_tags.py, delivered as merge requests
  • Agent-written configs and new analyses, possibly using the TopCPToolkit skill as a reference for CP algorithm YAML settings
Needs input

Decisions needed

Renumbered for v1.0. Each decision lists the options, a current leaning with the reason, and the milestone by which it must be settled. Items with an amber edge block M0.

D1

Whose identity does the agent act under at the facility?

Identity and securityby M0

The monitor runs for days, longer than a browser OAuth session. It needs to call the MCP gateway as the user throughout.

Options: per-user OAuth with refresh tokens stored by the agent service · a user-issued Personal Access Token from the MCP portal · a facility service account with jobs tagged by user.

Decided: a project-owned robot x509 certificate and/or service keytab for procedural ops. It is held only by a separate ops-executor pod and never by the agent process. Every job is tagged with the requesting user from the approval record, so per-user accounting survives. This still needs facility sign-off. Per-user delegation through the broker remains possible later, using the same executor. See Grid credentials for procedural ops.

D2

How do we reach HTCondor?

Compute and databy M0

The atlas-af gateway lists HTCondor as a backend, but its documented tool names cover identity, Rucio, AMI, JupyterLab and files. We need submit, query, history, edit, release, remove and log access.

Options: use the gateway's HTCondor tools as they are · contribute missing tools to the gateway · run our own small MCP server on a submit host using the HTCondor Python bindings.

Leaning: gateway first, contributing missing tools upstream. Our own server would duplicate the credential broker, which is the hardest part.

D3

How do HTCondor jobs get the EWKit image?

Compute and databy M0

EWKit's CI pushes images tagged by ref slug, so a branch tag moves with every push. Its workflow: rules appear to skip tag pipelines, so the tags productions run from may have no image at all. Workers must also be allowed to pull from the registry, and the image must tolerate a read-only filesystem, which Extend configs currently do not.

Options: apptainer pulls docker:// from gitlab-registry.cern.ch, using a read_registry deploy token if needed · publish EWKit images to /cvmfs/unpacked.cern.ch · build EWKit from source on the AF for each tag.

Leaning: ask the maintainers to add a tag rule to the CI workflow, then unpacked.cern.ch for tagged releases if they agree. Otherwise pull once per run into a cached image file on /data, pinned by digest and checked against the commit through the image's CI_COMMIT_SHA. Run with --writable-tmpfs until config_extended.yaml is written outside the install area. Either way, record the digest in provenance.

D4

Which refs may be run?

GitLab and EWKitby M1

EWKit requires a clean, pushed tag for grid productions and puts the tag in output names. Protected vX.Y tags are created only by maintainers, but most recent tags are per analysis (EFP_v6.6, EWK1L2L_v6.4, SlepWjetFF_v6.0), and which prefix belongs to which folder is not written down.

Options: any branch, tag or commit · any tag for full productions and branches or commits for test runs · protected vX.Y tags only.

Leaning: follow EWKit's practice. Full productions need a tag, per-analysis tags included; branches and commits are allowed for test-sized runs, named with a test suffix as --submissionTag does today. The validator enforces this from the RunSpec's purpose, and a prefix-to-folder map lets the builder suggest likely tags.

D5

Which GitLab credential does the service use to read EWKit?

GitLab and EWKitby M0

The FastAPI service needs to list refs, read the data/ tree and fetch files through the API.

Options: a project access token on EWKit (Reporter, read_api) · a group access token on the parent group · a CERN service account with a personal access token · per-user GitLab OAuth.

Leaning: a project access token created by an EWKit maintainer. It grants the least access, belongs to the project rather than a person, and maintainers can revoke it. Name an owner for yearly rotation.

GitLab and EWKitby M1

Leaning: on demand plus light polling. It needs no change to EWKit's settings, and a few minutes of delay does not matter for productions.

D9

What happens to folders that cannot run as they are?

D10

UChicago HTCondor only, or PanDA too?

Compute and databy M1

EWKit productions run on the grid today. Supporting PanDA would meet users where they are, but changes what the monitor watches.

Options: AF HTCondor only · AF plus PanDA via EWGridRun.py from the start · AF now, with the run model designed so a PanDA backend can be added.

Leaning: AF now, PanDA-ready design. Keep dataset-level clusters and grid-style output names so a later PanDA backend fits without changing the UI or the data model.

D11

How do jobs read their inputs?

Compute and databy M1

Leaning: XCache by default. Full lists run to thousands of DAOD_PHYS datasets, far beyond the 15 TB group disk, so replication stays an approved exception.

D12

Where do outputs go?

Compute and databy M1

Leaning: /data/<user> with EWGridRun names first. Add Rucio registration when a pilot team needs grid-style access, since it uses shared quota.

D13

May dataset names and job logs go to a hosted model API?

Leaning: confirm with ATLAS computing coordination during M0, since repository content reaches the model in M1 and logs in M2. The model sits behind one interface so the choice can change.

D14

Which models, and at what budget?

Agent designby M2

Leaning: tiered. Models are used in run setup, called once or twice per setup, and in the monitor, where most checks never call a model at all. Set a per-run token budget alongside the core-hour cap.

How do the builder agent and the Run setup form fit together?

D29

What does the reviewer see of the builder's work?

Agent designby M1

A reviewer that reads the builder's reasoning tends to agree with it. One that sees only the request and the spec judges the spec on its merits, but may repeat questions the builder already settled.

Options: the full builder conversation · the RunSpec and the builder's stated assumptions · the request and the RunSpec only.

Leaning: the request, the RunSpec and the validator report only. The builder's assumptions are shown to the person, who is the one who settles them. Revisit if evaluation shows the reviewer repeating settled questions.
