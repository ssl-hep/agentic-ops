IRIS-HEP · Design proposal

TopCP Agentic Ops

An assistant that runs TopCPToolkit n-tuple productions at the UChicago Analysis Facility, watches the HTCondor jobs, and proposes fixes that a person approves before anything changes. It starts from the config and input list a physicist commits to GitLab, and later learns to write both from a plain-language request.

Draft v0.4, for discussion Updated 7 October 2026 Stage Pre-implementation, no code yet Changes v0.2 monitor first, authoring and discovery in Phase 2 · v0.3 inputs arrive as GitLab commits · v0.4 deployment section

Summary

Producing TopCPToolkit (TCT) n-tuples is routine work that still takes a physicist days: writing and debugging a reco.yaml, finding the right DAOD containers for every DSID and MC campaign, splitting them into HTCondor jobs, and babysitting the queue for held jobs, XRootD read errors and memory overruns.

This proposal combines four existing pieces into one supervised workflow:

  • The topcptoolkit agent skill from the usatlas Claude marketplace, which encodes TCT config blocks, CLI options and known pitfalls. It drafts the YAML (Phase 2).
  • The UChicago AF MCP Platform (atlas-af at mcp.af.uchicago.edu), a credential-brokered gateway to Rucio, AMI, HTCondor and the AF filesystem. It runs and inspects the jobs, and in Phase 2 also finds the data.
  • LangGraph for durable, checkpointed agent graphs, one that authors and submits a production and one that monitors it for hours or days.
  • GitLab as the source of truth for inputs: the physicist's repository holds reco.yaml and the replica list, and the commit SHA becomes the production's identity.
  • CopilotKit for the web app, which shows live production state and renders the agent's proposed interventions as approval cards.

The work is split into two phases, monitor first. In Phase 1 the physicist commits their own reco.yaml and replica list to a GitLab repository, and every production is pinned to a commit. The system checks them, runs a test job, submits the production and monitors it, which puts the hardest and least-proven part (the monitoring agent and its approval loop) in front of users early. Phase 2 adds the agentic front end: drafting the YAML from a plain-language request with the TCT skill, and finding the samples through Rucio and AMI. Phase 2's agents deliver the same files to the same repository as merge requests, so nothing downstream changes.

The governing rule is simple: the model proposes, deterministic code executes, and a person approves anything that spends compute, writes data, or changes the physics configuration.

Goals and scope

Goals

  • Phase 1 Problems in a running production are noticed within minutes, explained in plain language with evidence, and paired with a concrete fix.
  • Phase 1 No production starts without a passing test job and an approved cost estimate.
  • Phase 2 A first-time TCT user gets a valid, runnable config and a correct sample list from a one-paragraph request.
  • Every action is attributable to a person and reproducible from recorded provenance (TCT tag, AnalysisBase release, YAML hash, sample list, skill version, model ID).

Out of scope for Phase 1

  • Drafting reco.yaml from a plain-language request (Phase 2).
  • Finding samples through Rucio and AMI (Phase 2). Phase 1 only checks the replicas the user supplies.
  • Writing custom C++ TCT algorithms or new config blocks.
  • Grid submission through PanDA (submitToGrid.py).
  • Downstream histogramming and fitting (FastFrames, TRExFitter, cabinetry).
  • Fully autonomous remediation with no human in the loop.

The last four are candidates for after Phase 2. See D4 and D5.

Architecture

Four runtime pieces plus the physicist's GitLab repository: a React web app with CopilotKit (Next.js assumed; see D22), a CopilotKit runtime that speaks the AG-UI protocol, a Python agent service running the LangGraph graphs (a submission graph and a monitor graph in Phase 1, with authoring steps added in Phase 2), and the existing UChicago MCP gateway. Postgres holds LangGraph checkpoints, application records and the audit log. GitLab notifies the agent service of new commits and receives commit statuses back, and in Phase 2 merge requests.

Components

Provided inputs and planning

Phase 1stages 1–2 · Gate B

Each analysis keeps its inputs in a GitLab repository. The physicist commits a reco.yaml (plus particle.yaml or parton.yaml if used), a replica list and a small production settings file, then starts a production from a specific commit. The production is pinned to that SHA, so the inputs cannot change underneath a running job. The system builds the sample manifest from the files, with each job cluster covering exactly one DSID and campaign. TCT requires this: mixing DSIDs corrupts CutBookkeeper normalisation. No model is involved at this stage; every check is deterministic.

Input checks

  • YAML parses; block names and keys exist in the TCT settings for the chosen release
  • Collection names match the input format (AnalysisJets for PHYSLITE, AntiKt4EMPFlowJets for PHYS)
  • Cut values look like MeV, not GeV
  • Every replica resolves through read-only Rucio calls; missing or unreachable files are listed
  • Each sample's files share one DSID and campaign; mixed groups are rejected with an explanation

Plan estimate shown at Gate B

  • Core-hours, from the test job's events/second, or a calibrated default before the test runs
  • Expected output size against the 5 TB /data quota
  • Queue choice: short (4 h limit) or long (72 h limit), and whether to allow MWT2 overflow
  • Files per job and number of jobs per sample
# proposed repository layout (one GitLab project per analysis)
my-ttbar-ntuples/
├── production.yaml   # TCT release, queue, output area, who may approve
├── reco.yaml         # TopCPToolkit config; particle.yaml / parton.yaml optional
└── samples.yaml      # replica list, one entry per DSID and campaign (D23)

GitLab integration

  • A push webhook tells the agent service about new commits; a periodic poll covers missed webhooks
  • Files are read at the exact commit through the GitLab API
  • Results go back as commit statuses with a link to the dashboard: input checks, test job, production state
  • Optional: the cheap checks (YAML lint, manifest schema) also run as a GitLab CI job the project includes

What starts a production

  • Commits alone only trigger input checks, so pushing work in progress is safe
  • A production starts when the physicist picks a commit in the web app, or pushes a tag matching an agreed pattern (D24)
  • A config fix during a run is a new commit, which becomes a new config version with its own test job

Open choices: the replica list format (D23), what triggers a production (D24), how the service connects to GitLab (D25), and where the input checks run (D26).

Request intake

Phase 2stage 2a

Physicists describe what they want in prose, and a structured form beside the chat fills in as the agent parses it. Either side can be edited. The output is a typed AnalysisRequest that later stages read instead of re-reading the chat.

Captured fields

  • Physics process and samples (DSIDs, or a description the agent resolves)
  • Data periods and MC campaigns (e.g. data22–24, mc23a/d/e)
  • Input format: DAOD_PHYS or DAOD_PHYSLITE, p-tag
  • Objects and working points, b-tagger, triggers
  • Event selection regions
  • Systematics: full, a named subset, or none
  • Analysis levels: detector, particle, parton

Agent behaviour

  • Asks clarifying questions only for fields that change the output, such as PHYS vs PHYSLITE or the tagger working point
  • Offers starting templates, e.g. ttbar lepton+jets or single-top t-channel
  • Can start from a reco.yaml already in the analysis repository

Config authoring

Phase 2stage 2b · Gate A

A LangGraph node runs a Claude agent with the topcptoolkit skill loaded. It writes the YAML block by block (CommonServices, Electrons, Muons, Jets, MissingET, OverlapRemoval, EventSelection, Thinning, Output) and attaches a short rationale to each block.

Deterministic checks before Gate A

  • All the Phase 1 YAML checks, reused unchanged
  • Cut values look like MeV, not GeV (a 25 in a pT cut is flagged)
  • The b-tag decoration in EventSelection matches the tagger and working point in Jets
  • Every container written in Output is produced upstream

What the reviewer sees

  • The YAML with an inline diff against the template or imported file
  • Per-block rationale that cites the skill's guidance
  • Predicted output branches, so they can confirm what will be saved
  • Edit in place, ask the agent to revise, or approve
  • The approved draft is pushed to a branch and opened as a merge request; merging it hands over to Phase 1 (D27)

Sample discovery

Phase 2stage 2d

The agent resolves the request into concrete containers using ami_* tools (physics parameters, AMI tags, hashtags) and rucio-atlas_* tools (DIDs, file lists, replicas). It writes samples.yaml in the Phase 1 format and opens a merge request. Once merged, it goes through the same input checks and Gate B.

Manifest columns

  • DSID, campaign, container name, p-tag
  • Files, events, total size
  • Replica availability at MWT2 and through XCache
  • Cross-section, k-factor, filter efficiency (from AMI)
  • Planned files per job and number of jobs

What discovery adds over Phase 1

  • Choosing containers from a physics description instead of a list
  • Picking the right p-tag and AMI tag for each campaign
  • Preferring containers with complete replicas near MWT2
  • Pulling AMI totals so completion can be checked against expected event counts

Build, test and submit

Phase 1stages 4–6 · Gate C

TCT is compiled from source against AnalysisBase 25.2.x. Where that build lives is an open decision (D3); the working assumption is a container image per TCT release tag so that jobs do not compile anything. Submission generates one HTCondor cluster per manifest row, following AF conventions.

# sketch of a generated submit description (illustrative, not final)
universe                = vanilla
executable              = run_tct.sh          # wraps runTop_el.py -i inputs_$(ProcId).txt -o out
+SingularityImage       = "<TCT image for tag vX.Y.Z>"
+queue                  = "short"             # or long, chosen at Gate B
+ALLOW_MWT2             = True                # overflow, if approved
request_cpus            = 1
request_memory          = 2GB
use_x509userproxy       = true                # proxy minted by the broker? see D1
log    = logs/$(ClusterId).log
output = logs/$(ClusterId).$(ProcId).out
error  = logs/$(ClusterId).$(ProcId).err
+AgenticOpsProduction   = "<production id>"   # custom ClassAd for tracking
queue $(nJobs)

Test job checks

  • Exit code zero and a reco tree present
  • CutBookkeeper and listOfSystematics histograms present
  • Branch list matches what the Output block asks for
  • Events/second and peak memory, used to size the full run

Submission safeguards

  • Idempotency key per cluster, so a retried submit cannot double-submit
  • Hard cap on jobs and core-hours per production, set at Gate B
  • Custom ClassAd tag on every job so the monitor can find them

Monitoring agent

The monitor is a LangGraph graph with one thread per production, checkpointed in Postgres so it survives restarts. It does not sleep in-process. Each check is a short run triggered on a schedule, which keeps load on the schedd predictable and lets a production be paused by simply not scheduling the next check.

Detection is rule-based and cheap: state counts, hold reasons, exit codes, time spent idle, throughput against the plan. The model is called only when a rule fires, to read the evidence, diagnose the cause, and draft an intervention from a fixed catalogue.

What it watches

  • Job state counts per cluster: idle, running, held, completed, removed
  • Hold reasons, e.g. memory over request, proxy expired, file transfer failure
  • Idle time beyond the norm, with the equivalent of condor_q -analyze
  • Failed exits, with the tail of stderr parsed for known TCT and XRootD signatures
  • Throughput against the Gate B estimate
  • Output files arriving in /data, opened with uproot for a quick check

Completion criteria

  • Every input file was processed exactly once, or an explicit, approved exclusion list exists
  • The sum of CutBookkeeper initial events matches the expected total for each sample: from Rucio file metadata in Phase 1, and from AMI as well once discovery arrives in Phase 2
  • No output file is zero-length or missing the reco tree
  • A provenance record is written next to the outputs

When to stop retrying and accept a partial production is decision D20.

Interventions

The agent can only propose actions from a typed catalogue. Each entry has a fixed implementation, a risk level and a default approval policy. The model fills in parameters and writes the explanation; it cannot invent new kinds of action.

Web app

A React application (Next.js assumed, see D22) using CopilotKit's LangGraph integration. Shared agent state streams to the browser over AG-UI, so the dashboard and the chat always show the same picture. A chat sidebar is available on every screen for questions like "why is the single-top sample slower than ttbar?"

Deployment

The system ships as two container images, a web image and an agent image, plus Postgres. Both images sit behind one hostname, so the browser sees a single origin. That avoids cross-origin configuration and keeps one sign-in session cookie for the whole app.

Agent service: FastAPI with LangGraph as a library

LangGraph is a Python library, so graphs can run inside any process. There are two ways to host them.

The agent image runs as two processes that share Postgres, so a slow web request can never hold up a monitor check, and the reverse is also true:

  • agent-api serves the AG-UI endpoint, the GitLab webhook and the REST API for the dashboard and audit log. It holds no state of its own, so it can scale to several replicas.
  • agent-worker runs the scheduled monitor checks and the submission steps. It starts as a single replica, which avoids any need for leader election.

LangGraph Studio and langgraph dev remain available on developers' laptops for debugging graphs, whichever server runs in production.

Topology

Environments

  • Local: Docker Compose with Postgres, the agent image and the web app. A stub MCP server replays recorded job histories, so monitor work needs no facility access.
  • Staging: its own namespace on the hosting cluster, a test GitLab project, and the real MCP gateway with a test account.
  • Production: its own namespace, with Postgres backed up and the audit log retained per D19.

Build and release

  • GitLab CI builds both images on every merge and pushes them to the project's container registry
  • Tagged releases deploy to production; the default branch deploys to staging
  • Deployment tooling (Helm, Kustomize or Argo CD) is decision D28

Secrets

  • GitLab OAuth application secret and webhook token
  • Model API key
  • Per-user MCP and GitLab tokens, encrypted at rest in Postgres, if D1 and D25 settle on stored user tokens
  • All held as Kubernetes secrets, never in images or repositories

Safety and trust

Guardrails

  • Typed intervention catalogue; no free-form shell or condor_* commands from the model
  • Per-production caps on jobs, core-hours and output size, enforced in code
  • A kill switch per production and a global one for operators
  • Write tools available only to the execution node, never to the diagnosis node
  • Approvals expire if the underlying state has changed since the card was created

Untrusted input

  • Job stdout and stderr, file names, dataset metadata, and YAML comments and commit messages from GitLab are data, not instructions. They are passed to the model inside clearly delimited evidence blocks.
  • Nothing read from a log can widen the agent's permissions or skip an approval, because policy checks run in code after the model responds.
  • Log excerpts are truncated and summarised before reaching the model, to limit both cost and injection surface.

Accountability

  • Every MCP call runs as the requesting user through the broker, so facility logs show who acted
  • The audit log records which model and skill version produced each proposal
  • Provenance is written next to the outputs for later reproduction, keyed by GitLab project and commit SHA

Evaluation

Monitoring Phase 1

  • Recorded job histories replayed through the graph: held for memory, proxy expiry, bad replica, slow site, a corrupt input file
  • Metrics: time to detection, correct diagnosis rate, false alarm rate, approval acceptance rate
  • Shadow mode in production first: the agent proposes, nobody acts, and operators compare its proposals with what they actually did
  • Phase 1 users bring productions they would run anyway, which gives realistic failure data early

Config authoring Phase 2

  • A golden set of requests paired with reviewed YAML. The configs committed during Phase 1 are a natural source, with history showing how each one was fixed.
  • Pass criteria: deterministic checks pass, and a 1,000-event local run succeeds
  • Metric: share of drafts approved at Gate A with no edits, and median edits per draft

Needs input

Decisions needed

Each decision lists the options, a current leaning with the reason, and the milestone by which it must be settled. Items with an amber edge block M0 and should be resolved first.

D1

Whose identity does the agent act under?

Identity and securityby M0

The monitor runs for days, longer than a browser OAuth session. It needs to call the MCP gateway as the user throughout.

Options: per-user OAuth with refresh tokens stored by the agent service · user-issued Personal Access Token from the MCP portal · a facility service account with jobs tagged by user.

Leaning: per-user delegated OAuth through the broker, with PATs as a fallback. A service account breaks per-user accounting and quota and needs facility sign-off.

D2

How do we reach HTCondor?

Compute and databy M0

The atlas-af gateway lists HTCondor as a backend, but its documented tool names cover identity, Rucio, AMI, JupyterLab and files. We need submit, query, history, edit, release, remove and log access.

Options: use the gateway's HTCondor tools as they are · contribute the missing tools to the gateway · run our own small MCP server on a submit host using the HTCondor Python bindings.

Leaning: gateway first, contributing missing tools upstream. Running our own server duplicates the credential broker, which is the hardest part.

D3

Where is TopCPToolkit built?

Compute and databy M0

TCT is compiled from source against AnalysisBase 25.2.x. Jobs need a ready build.

Options: a container image per TCT release tag, built in CI · a build in the user's $HOME per production · compile inside each job.

Leaning: one image per release tag, published where AF workers can read it. It is reproducible and avoids per-job compile time. Custom algorithms would later need an overlay image.

D4

Which TCT features does the authoring agent support?

Agent designby M5

Phase 1 runs whatever valid YAML the user uploads, as long as it needs no custom code beyond the standard TCT image. This decision is about what the Phase 2 agent can draft, which drives the golden set.

Options: detector level only · detector plus particle level · all three levels including parton history · plus custom C++ algorithms.

Leaning: detector and particle level, standard blocks only. Parton history and custom code come after the Phase 2 pilot.

D5

Is UChicago HTCondor the only execution backend?

Compute and databy M1

Large productions may be better suited to the grid via PanDA, which TCT supports with submitToGrid.py.

Options: UChicago AF only · AF plus PanDA from the start · AF now, a pluggable backend interface for later.

Leaning: AF only, with a backend interface kept in mind. The UChicago gateway makes AF the fastest path.

D6

How do jobs read their inputs?

Compute and databy M1

Options: stream through XCache (root://) · replicate to MWT2_UC_LOCALGROUPDISK with a Rucio rule first · a mix decided per sample.

Leaning: XCache by default. Replication is an approved intervention for samples with poor replica availability, since it uses shared group quota.

D7

Where do outputs go, and are they merged?

Compute and databy M1

Options: /data/<user> (5 TB, not backed up) · registered in Rucio on LOCALGROUPDISK · object storage. Also: keep one file per job, or merge per sample with hadd.

Leaning: /data/<user> with a fixed directory convention, no merging in v1. Rucio registration is worth adding once outputs are shared within a group.

D8

How is the TCT skill loaded inside LangGraph?

Agent designby M5

Agent skills are designed for Claude Code and the Claude Agent SDK, which load them on demand. LangGraph does not do this natively.

Options: run a Claude Agent SDK sub-agent inside the authoring node, which loads skills natively · use the Claude API's skills support · read SKILL.md and its references into the prompt ourselves.

Leaning: Agent SDK sub-agent for authoring, pinned to a marketplace git SHA. It keeps progressive loading of the reference files and stays in sync with upstream.

D9

May ATLAS metadata and logs go to a hosted model API?

Identity and securityby M0

Dataset names, configs and job logs would be sent to the model provider. ATLAS data-handling policy may restrict this.

Options: hosted Claude API under an institutional agreement · Claude through a cloud provider with a data-residency commitment · a self-hosted open model for some or all stages.

Leaning: confirm with ATLAS computing coordination before the monitor starts sending job logs to a model in M2. The architecture keeps the model behind one interface so the choice can change.

D10

Which models for which stages, and at what budget?

Agent designby M2

Options: one strong model everywhere · a strong model for authoring and diagnosis, a small fast model for log triage and summaries.

Leaning: tiered. In Phase 1 the only model use is monitor diagnosis. Most checks never call a model at all; those that do mostly need summarising. Set a per-production token budget alongside the core-hour cap.

D11

Where do the agent service and web app run?

Operationsby M1

Options for where: AF Kubernetes at UChicago · CERN's OpenShift platform · an IRIS-HEP or institutional cluster · LangChain's managed cloud. Options for how: LangGraph's Agent Server (standalone production use needs a LangSmith license) · our own FastAPI service with LangGraph as a library and a Postgres checkpointer.

Leaning: our own FastAPI service on AF Kubernetes, close to the MCP gateway, as described under Deployment. It needs no license, keeps data on facility infrastructure, and hosts the GitLab webhook and REST API we need anyway. CERN OpenShift is the fallback if AF cannot host services or webhooks cannot reach it.

D22

Which frontend framework?

Product and UXby M1

CopilotKit's first-class SDKs are React and Angular. The hooks this design relies on (useCoAgent, useLangGraphInterrupt) and the prebuilt chat UI are React components. Svelte and Vue have community adapters only. The CopilotKit runtime and the AG-UI protocol work with any frontend.

Options: React with Next.js · React with Vite (no server rendering needed) · SvelteKit talking AG-UI directly through the framework-agnostic @ag-ui/client, building our own chat panel and approval cards · Angular.

Leaning: React, because CopilotKit's interrupt and shared-state features come ready-made. Next.js itself is not required. SvelteKit is viable if the team's Svelte experience outweighs rebuilding the chat and interrupt UI, which adds frontend work to M1 and M3. With Next.js the CopilotKit runtime lives in the same container as the pages; a Vite build needs a separate small Node runtime container.

What format does the replica list take?

Compute and databy M1

Phase 1 depends on users supplying their inputs. The format decides how much the system can check, and whether Phase 2 discovery can produce it directly.

Options: TCT-style inputs.txt files, one per sample, with one file path or root:// URL per line · a list of Rucio dataset or container names that the system expands read-only · a small YAML manifest with sample name, DSID, campaign and either names or file paths per row.

Leaning: the YAML manifest, with Rucio names preferred over raw paths. Names let the system pick XCache paths, check completeness and read event counts. Raw paths are accepted as a fallback, with DSID and campaign then inferred from file names and confirmed by the user. It is committed as samples.yaml, and Phase 2 discovery would emit the same file.
